# Day 47 — Users, Foreign Keys, and Database Constraints

## What I worked on

Today I extended the Notes API and database to support users and a relationship between users and notes.

The main goal was to learn how **foreign keys, existing data, API models, service-layer logic, and database constraints** work together.

The resulting relationship is:

```text
users
  │
  │ 1
  │
  │
  │ many
notes
```

Each note belongs to one user, while a user can have multiple notes.

---

## 1. Created the `users` table

I created a new Alembic migration for the `users` table.

The table contains:

* `id` — integer primary key generated by PostgreSQL
* `username` — text value that must be unique and cannot be NULL

The migration created a unique constraint for `username`.

This means two users cannot have the same username.

Example users:

```text
id | username
---+---------
1  | Alice
2  | Emily
3  | Sakura
```

---

## 2. Added a foreign key to `notes`

I added a `user_id` column to the `notes` table.

The column references `users.id`:

```text
notes.user_id → users.id
```

This is a **foreign key**.

A foreign key ensures that a value in one table must correspond to an existing value in another table.

For example:

```text
notes.user_id = 1
```

is valid because user `1` exists.

But:

```text
notes.user_id = 999
```

is invalid if user `999` does not exist.

I tested this directly in PostgreSQL and received a foreign-key violation when trying to insert a note with a nonexistent user.

---

## 3. Migrated existing notes

The `notes` table already contained data before the relationship was introduced.

Initially, the new `user_id` column was allowed to contain `NULL` values.

This was necessary because the existing notes did not have an owner yet.

I created users and assigned the existing notes to them.

For example:

```sql
UPDATE notes
SET user_id = 1
WHERE user_id IS NULL;
```

I then moved some notes to Emily:

```sql
UPDATE notes
SET user_id = 2
WHERE title IN ('JavaScript', 'HTML', 'CSS');
```

I also used a `JOIN` to verify the relationship:

```sql
SELECT notes.id, notes.title, users.username
FROM notes
JOIN users
ON notes.user_id = users.id
ORDER BY users.id, notes.id;
```

This showed which user owned each note.

---

## 4. Made `user_id` required

After verifying that all existing notes had a valid user, I created another Alembic migration to make `notes.user_id` `NOT NULL`.

Before:

```text
user_id integer
```

After:

```text
user_id integer NOT NULL
```

This creates an important distinction:

### API validation

The Pydantic model contains:

```python
user_id: int
```

This protects the API from requests that don't contain a valid integer user ID.

### Database constraint

PostgreSQL contains:

```text
user_id integer NOT NULL
```

This protects the database itself from notes without a user.

The database also has the foreign key constraint, so together these constraints ensure that every note must reference an existing user.

The migration was tested successfully with:

```bash
alembic upgrade head
```

and:

```bash
alembic current
```

The final migration became the Alembic `head`.

## 5. Updated the Pydantic models

I added separate models for creating and returning users:

```python
class UserCreate(BaseModel):
    username: str = Field(min_length=3)


class UserResponse(BaseModel):
    id: int
    username: str
```

This follows the same request/response separation used by the Notes API.

`UserCreate` describes what the client is allowed to send.

`UserResponse` describes what the API returns, including the database-generated ID.

I also added `user_id` to the note models.

## 6. Updated the notes service

The notes service was updated so that queries include `user_id`.

For example, the `SELECT` queries now retrieve:

```sql
SELECT id, title, content, created_at, user_id
FROM notes
```

Creating a note also inserts its user:

```sql
INSERT INTO notes (title, content, user_id)
VALUES (%s, %s, %s)
```

The returned note therefore contains its `user_id`.

When updating a note, I did not update `user_id`.

The update only changes:

```text
title
content
```

The existing owner is retrieved from the database.

This is important because changing a note's content should not automatically change its owner.

## What I learned

### Primary key vs foreign key

A **primary key** identifies a row within its own table.

Example:

```text
users.id
```

A **foreign key** stores a reference to a row in another table.

Example:

```text
notes.user_id → users.id
```

The primary key answers:

> "Which row is this?"

The foreign key answers:

> "Which row in another table is this related to?"

---

### Foreign keys enforce relationships

A foreign key isn't just information describing a relationship.

PostgreSQL actively enforces it.

This means the database prevents invalid references such as:

```text
notes.user_id = 999
```

when user `999` doesn't exist.

---

### Constraints should exist at the database level

API validation is useful, but it should not be the only protection.

The database now independently enforces:

```text
username NOT NULL
username UNIQUE
notes.user_id NOT NULL
notes.user_id → users.id
title minimum length
content minimum length
```

This makes the database more reliable even if data comes from somewhere other than the FastAPI application.

---

### Safe database migrations

I learned that when adding a required relationship to an existing database, it is often necessary to do it in stages:

```text
1. Create the related table
        ↓
2. Add the foreign-key column
        ↓
3. Allow NULL temporarily
        ↓
4. Migrate existing data
        ↓
5. Verify the data
        ↓
6. Add NOT NULL
```

Making the column `NOT NULL` immediately would have failed because existing rows did not have a `user_id`.

---

## Current database relationship

The final structure is:

```text
users
----------------
id          PK
username    UNIQUE NOT NULL
       │
       │
       │ 1
       │
       │
       │ many
       ▼
notes
----------------
id          PK
title       NOT NULL
content     NOT NULL
created_at  NOT NULL
description
category
user_id     FK → users.id, NOT NULL
```

This is my first proper example of a **one-to-many database relationship** in the project.

---

## Important design note

For now, the API accepts `user_id` in the request when creating a note:

```json
{
    "title": "Example",
    "content": "Example content",
    "user_id": 1
}
```

This is acceptable for the current learning stage.

However, this is not how the final authenticated application should work.

Later, when authentication is implemented, the authenticated user's identity should determine the owner of the note instead of trusting an arbitrary `user_id` supplied by the client.

---

## Main takeaway

Today I connected several layers of the application:

```text
PostgreSQL
    ↓
Foreign key + constraints
    ↓
Alembic migrations
    ↓
Service layer
    ↓
Pydantic models
    ↓
FastAPI routes
    ↓
Swagger
```

The important lesson is that a database relationship isn't just a change to one SQL table. The relationship needs to be represented and handled consistently throughout the application.
