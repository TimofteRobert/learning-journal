# Day 35 – Adding `created_at` to the backend

## Goal

Continue implementing a creation date (`created_at`) for every note by updating the backend layer by layer instead of modifying everything at once.

---

## What I learned

### 1. Database-first development

I added a new `created_at` column to the PostgreSQL database.

Instead of generating the date in the frontend, the database generates and stores the timestamp automatically. This ensures every client receives the same creation date and keeps the data consistent.

---

### 2. Response models vs request models

I updated `NoteResponse` to include:

* `id`
* `title`
* `content`
* `created_at`

I intentionally did **not** add `created_at` to `NoteCreate` because the client should not send values that are generated by the database.

---

### 3. Updating helper functions

I modified `make_note()` to accept four parameters:

* id
* title
* content
* created_at

Because this helper is used throughout the service layer, updating it in one place made the rest of the changes much easier.

---

### 4. Updating SQL queries

I updated every query that returns a note so it also returns the `created_at` column.

This included:

* `get_notes()`
* `get_note_by_id()`

---

### 5. PostgreSQL RETURNING

I learned that PostgreSQL can immediately return values generated by the database.

For inserts:

```sql
INSERT ...
RETURNING id, created_at;
```

For updates:

```sql
UPDATE ...
RETURNING created_at;
```

This avoids executing an additional SELECT query after creating or updating a note.

---

### 6. Reading code patterns

While modifying the project I noticed that similar database operations follow similar patterns.

Instead of memorizing code, I started recognizing reusable patterns:

* execute SQL
* fetch returned values
* commit transaction
* build response with `make_note()`

---

### 7. Debugging my own code

During the implementation I made several mistakes and corrected them during review:

* forgot to add `created_at` as a function parameter
* tried to use `note.created_at` even though the frontend never sends it
* supplied too many SQL parameters
* added a comma before `RETURNING`
* learned that `RETURNING` belongs inside the SQL statement and returned values are read afterwards with `fetchone()`

Understanding **why** these mistakes happened helped me understand the flow of data between the frontend, backend, and database much better.

---

## Key takeaway

A value generated by the database should stay the responsibility of the database.

The backend retrieves that value using `RETURNING`, includes it in the response model, and sends it to the frontend without requiring the client to create or modify it.
